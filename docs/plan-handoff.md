## 六、项目：基于 C++ 的 KV 缓存引擎（LRU 淘汰）

> **MVD（最小可投版本）= CLI + `get`/`put` + 淘汰 + 持久化**
> **W4 结束（11/15）必须能跑 —— 这是简历的保险，比 benchmark 重要 10 倍。**

| 周 | 目标 | 交付物 | 检查点 |
| --- | --- | --- | --- |
| W1 | `Node`（key/value/prev/next）+ 双向链表 `addToHead`/`removeNode`/`moveToHead`；CLI 骨架能读命令 | `src/list.cpp` + `main` 里手动调链表 | 能画出手动插入/删除后的指针变化 |
| W2 | `LRUCache` 框架（capacity / unordered_map / 头尾哑节点）+ `get()` 命中移头部 | `src/lru_cache.cpp` | 能演示「put 三个，get 其中一个，顺序变了」 |
| W3 | `put()` + 淘汰（满则删尾并同步删哈希）；边界：容量 1 / 连续 put 同 key / get 后 put 触发淘汰 | 测试 + 首个像样的 commit | 146 题独立一次 AC |
| W4 | `dumpFile` / `loadFile`（自己解析格式、跳过非法行） | `src/persistence.cpp` | put 一批 → 退出 → 重开 → get 验证 ★ **MVD 冻结** |
| W5 | 线程安全：**一把全局 mutex** 保护 `cache` 与链表操作；**4 线程**简单压测 | `src/thread_safe.cpp` + 压测脚本 | 能说「多线程下加锁保护，4 线程 X 万 QPS」 |
| W6 | benchmark：**命中率 vs 容量（10/100/1k/10k）+ LRU vs FIFO vs 随机**；README（数据流向图 + 表格） | README + `docs/benchmark.md` | 把 GitHub 链接发给朋友，他能看懂这是什么 |

**W5 的边界（定稿，不再改）**：只做**全局 mutex + 4 线程压测**，只求一个 QPS 数字和一段讲得清的并发故事。

**分段锁不做**，理由是面试风险不对称：
- 写了分段锁（80 分的并发）→ 面试官必然追问「get 里的 moveToHead 锁覆盖到了吗」「多段加锁顺序怎么防死锁」「锁竞争怎么测的」，当场露怯 → 掉到 50 分
- 只写全局 mutex（60 分的并发）→ 面试官反问「再往上怎么优化」，答「整表一把锁会串行化，往上要按哈希分桶做分段锁，这是下一步升级方向」→ 稳的 60 分

所以分段锁降级为**入职后的升级方向**，简历里只写「预留按哈希分桶的分段锁扩展」。

**不做**：手写链地址法哈希、分段锁、无锁队列。

**面试话术**
- 原理（1 分钟）：哈希表定位 + 双向链表维护使用顺序，头部是最近使用、尾部是最久未用，两者配合实现 O(1) 查询和 O(1) 淘汰
- 并发（1 分钟）：用一把全局 mutex 保护哈希表和链表，get/put 全程加锁，4 线程压测 X 万 QPS
- 局限（主动说，加分）：LRU 怕顺序扫描污染缓存，工程上会用 LRU-K / 2Q / SLRU
